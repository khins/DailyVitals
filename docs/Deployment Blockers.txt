Deployment Blockers
Before putting real health information online, address these:
Connection configuration - resolved
DailyVitals accepts ASP.NET configuration plus DAILYVITALS_CONNECTION_STRING and
ConnectionStrings__DailyVitals environment variables, with App.config retained only
as a desktop-development fallback.

Local secrets - resolved
Local database and API credentials are excluded from Git, Docker build context, and
web publish output. DailyVitals.Web uses .NET user-secrets or environment variables;
machine-local App.config files are no longer tracked.

Authentication - resolved
DailyVitals.Web now uses ASP.NET Core cookie authentication. Username, person_id, and demo access
are server-issued claims in an encrypted HTTP-only cookie; health routes require
authorization. Browser local/session storage is no longer trusted.

Database migrations - resolved
Schema changes are tracked as ordered SQL migrations with checksums, advisory locking,
and transactional execution. Data services no longer invoke schema setup during
requests. Production uses `dotnet DailyVitals.Web.dll --migrate-only`; application
startup refuses to continue when migrations are pending.

Durable encryption keys - resolved
Production startup now requires an absolute DataProtection__KeysPath backed by a
persistent volume and an absolute DataProtection__CertificatePath pointing to a
PKCS#12 certificate with a private key. The key ring is encrypted with that
certificate, and startup fails rather than silently using ephemeral deployment
storage. Development retains the ignored App_Data fallback.

Recommended Architecture
First release:
Browser -> HTTPS -> DailyVitals.Web -> Managed/private PostgreSQL
                              |
                              +-> OpenAI API
Future WPF release:
Browser/WPF -> HTTPS -> DailyVitals.Api -> DailyVitals.Data -> PostgreSQL
Keep DailyVitals.Domain or a new DailyVitals.Contracts project shared. Keep DailyVitals.Data exclusively on the server. Never distribute production database credentials inside the WPF application.
First Deployment Sprint
I recommend starting with a read-only Demo Mode deployment containing only synthetic data:
Add environment-variable database configuration.
Add production-safe configuration validation.
Validate the baseline and migration runner against a production-like database copy.
Add /health readiness and liveness endpoints.
Add a Dockerfile and strict .dockerignore.
Provision a separate staging PostgreSQL database.
Deploy Demo Mode without the OpenAI key.
Verify HTTPS, persistent keys, logs, backups, and read-only enforcement.
Verify cookie sign-in, sign-out, expiration, and route authorization in staging.
This gives you a working public portfolio deployment while keeping real health data out of the first infrastructure experiment. The existing [deployment guide](C:\\Users\\Kevin\\source\\repos\\DailyVitalsApp\\docs\\deployment.md) already points in this direction; the next step is choosing whether your server will be Windows/IIS, Linux/Docker, or a managed application platform.
